Stage 7: does embedding a local decision model (Kev-4B) in DuckDB bring something a cloud API cannot?

Three candidate benefits are tested, each with its own line fixed below: (A) the local model as a semantic-SQL backend on a published
benchmark, (B) the server's cache of texts it has already read, used as a "semantic index", (C) calibration parameters fitted on a
few human labels and stored in the database like statistics. Everything runs on this machine (Apple M3 Max, 64 GB). No paid API is
called. Jev, the cheap LLM and the published systems appear only as comparison columns taken from the cached results of earlier
stages.

What was known when this was written
- Stages 1 and 6 (database/README.md). For Kev-4B in particular: its accuracy, AUC, Brier score, calibration and throughput on 5,000
  movie reviews (question "positive"), 1,000 restaurant sentences x 21 predicates and the Walmart-Amazon test set, and what
  recalibration with 200 human labels does on those three datasets (stage 6, secondary analysis).
- Kev-4B has never been asked: any pair, choice or score question of the SemBench queries; the question "clearly positive"; any
  Rotten Tomatoes review outside the two SemBench samples; any pair of abt-buy, amazon-google or dblp-acm; any pair of a validation
  split.
- The Kev authors' own figures for the cache (their README): five questions about a 270-token text, 721 ms the first time and
  136 ms after that; a 65,000-token document 84.5 s, then 0.7 s (both on an M5).
- A planning probe on made-up rows only (2026-10-11; 300 invented reviews, 24 invented documents, none in any dataset; answers not
  examined). Later questions on a cached text were faster by about 1.4x-2.0x for 46-token reviews and 10x-69x for documents of
  1,400-9,800 tokens. Every cached text cost about 55 MB of server memory whatever its length, plus about 32 KB per token; 320 cached
  reviews grew the server from 8.5 to 27.6 GB. The fixed part follows from the architecture (24 Gated DeltaNet layers, each keeping a
  32 x 128 x 128 fp32 state). So, before any real row was asked, it was already likely that line B1 below is met by a wide margin,
  that the short-text speed line is missed or borderline, and that a cache for a whole short-text table does not fit in memory. The
  lines are kept as written; these expectations are recorded so that the result is not read as a surprise.

    mams    the first 300 sentences of the fixed stage-4 order; the first three of the 21 predicates (mention:food, mention:staff,

- Arms: off (KEV_PREFIX_CACHE=0), table (cache large enough for every row of the dataset), default (shipped: 4 texts).
- One run = one dataset x one arm on a freshly started server: warm-up on made-up rows of the same kind (every question once), then
  the same rows asked one question per pass, concurrency 1, in blocks; after each block the server's hit/miss counters and the
  server's memory (footprint -f bytes) are read, outside the timed intervals. The off arm ends with one pass that packs all the
  questions into one request (reference). Answers are stored and not looked at before all collection is finished.
- Repetitions: off and table three times each for movie, mams and long, in the order off/table, table/off, off/table; default
  once; the four shorter tiers off and table once.
- Primary measure, per dataset: later-question speedup = (sum over questions 2..K of the median seconds with the cache off) /
  (the same with the table cache).
- Mechanism check: in the table arm every request of question 1 is a miss and every request of the later questions is a hit; in the
  off arm there is no hit. A dataset where this fails is reported as failed; nothing is patched.
- Fidelity: an answer's decision is p >= 0.5 (yes/no), the chosen option (choice), the most probable level (score). Agreement =
  share of answers of questions 2..K, all repetitions, whose decision with the table cache equals the decision with the cache off;
  a missing answer counts as different. Also reported: mean and largest probability difference, question 1, and repeat runs of
  the same arm.
- Memory model: least squares without intercept on the block readings of the first table run of every dataset,
  (footprint - footprint after warm-up) = a * texts cached + b * request tokens of question 1. Capacity: with a budget of 24 GB for
  the cache (64 GB machine, 8.5 GB of weights), does the cache for a whole table fit - the 40 documents; the 1,864 distinct review
  texts of the SemBench sample; the 3,949 MAMS sentences (tokens per text taken from the 300-row samples).
- Lines
    B1  long documents: later-question speedup >= 3.
    B2  agreement >= 99.5% on each of movie, mams, long (99.5% is what Jev agrees with itself when asked twice).
    B3  the cache fits the 24 GB budget (by the memory model).
  "The cache works as a semantic index for long documents" = B1 and B2 (long) and B3 (the 40 documents).
  "It works for whole short-text tables" = later-question speedup >= 2 on both movie and mams, and B2 on both, and B3 for both whole
  tables.
- Reported next to the lines: the cost of building the cache (question 1, table against off); the default arm; the packed pass;
  speedup against measured tokens across all seven datasets; per-row latency; later-question rows per second against Jev's cold
  throughput on the same kind of data (stage-6 reference figures); the spread between repetitions (a spread above 15% is flagged).

Part C. Calibration parameters stored in the database (src/jevsql/calibration.py, database/p7_calibration.py)
- Form: table semantic_calibration(model, predicate, scope, a, b, ...); macro calibrated(p, model, predicate, scope) =
  sigmoid(a + b * logit(p)) with the parameters looked up by the database, p clipped to [0.001, 0.999]; raw p when no parameters
  exist; kev_noul_cal / kev_noulc_cal apply it to the model's answer. Fit: the stage-6 recalibration (a + b * logit(p) by maximum
  likelihood with Platt's target smoothing), on human labels only.
- Data: the record-matching datasets of entity_match/. Fresh for Kev: abt-buy, amazon-google (product question) and dblp-acm
  (publication question). Seen in stage 6: walmart-amazon (product question). Questions and states are the ones Jev answered.
    label pool  1,000 pairs of the validation split (first 1,000 by hash of the pair id with salt "p7:<dataset>");
    stored fit  the first 200 pairs of the pool, scope = the dataset;
    test        the whole test split, one SQL statement returning the raw probability, the probability calibrated with the
                dataset's own parameters, and the probability calibrated with walmart-amazon's parameters.
- Reference: Jev's cached judgments on the same test pairs (out/entity_match), as served, no labels.
- Rule (the stage-6 rule): a source matches Jev on a test set if accuracy >= Jev's - 2.0 points, AUC >= Jev's - 0.02 and Brier <=
  Jev's + 0.02, paired on the same pairs; more than 5% unanswered fails. Point estimates decide; 2,000 bootstrap resamples of pairs
  give 95% intervals, and a difference whose interval contains the bar is reported as not separable from it.
- Line C: "stored calibration works" = with its own stored parameters Kev-4B matches Jev on all three fresh test sets, and as served
  (raw) it fails on at least one of them. If raw already matches on all three: reported as "calibration not needed", not as an
  effect. If the calibrated model fails anywhere: not met, with the failing condition named (the calibration is monotone, so it
  cannot move AUC).
- Reported next to the line: accuracy, AUC, Brier, equal-mass calibration error, precision, recall, F1; the change raw -> calibrated
  with intervals; the largest difference between the probability computed in SQL and the same formula in Python (anything above
  1e-9 is a bug); transfer (walmart-amazon's parameters on abt-buy and amazon-google, the same predicate on other tables; dblp-acm
  has another predicate, so the macro must return the raw probability there); label counts 25 / 50 / 100 / 200 / 500 drawn 200
  times from the pool; on walmart-amazon, agreement of today's answers with the ones collected in stage 6.

  predicates are replayed from its cache through the SQL functions with no request sent; one parameter pair per predicate fitted on

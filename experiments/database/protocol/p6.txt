Data and questions (nothing new is written or edited; every backend gets the same state and question payload Jev answered)
- movie  the 5,000 review texts that every open-model source judged in stage 2 (5,001 labelled rows), question "positive",
         truth scoreSentiment = POSITIVE.
- mams   the fixed 1,000 sentences of stage 4, 21 predicates, one question per request. Truth as in stage 4.
- em     the Walmart-Amazon test set, all 2,049 pairs, the product question of entity_match/run.py. Truth: the benchmark label.
A decision is p >= 0.5 for every source. No threshold, prompt or temperature is tuned for any backend.

Collection
- New cache namespace "p6:", so every run is cold. Failed requests are re-asked in up to 4 passes. A request still without a usable
  answer counts as wrong in accuracy and as p = 0.5 everywhere else, and the number of such requests is reported.
- Concurrency per backend is set by a speed probe on 200 movie texts outside the 5,000 (concurrency 1, 4, 16; the fastest is used).
  The probe's answers are not examined.
- Hosted backends: before the main run, 20 requests of each kind (movie, restaurant single, restaurant packed, pair) are sent to
  read the billed tokens per request (answers not examined). If the projected total for the approved hosted backends exceeds the
  amount the user approved, stop and report.

Metrics, per backend and dataset (restaurant data: per predicate, then averaged over the 21)
- accuracy against the human labels; AUC; Brier score = mean (p - y)^2;
- expected calibration error with 10 equal-width bins (the function used in stage 3) and with 10 equal-mass bins;
- the reliability table itself with the number of rows per bin, and for the middle band 0.1 <= p <= 0.9: number and share of rows,
  mean p against the share of positives, accuracy. A calibration figure is not to be read off the top bin alone;
- error concentration: the share of the backend's own errors that lie in its own least-sure 10 / 20 / 30 / 50% of rows (smallest |p - 0.5|);
- batch throughput: rows per second of the cold main run (wall clock, retries included); cost per 1,000 rows (list price times the
  input tokens the service reports; local backends are reported as free, hardware and electricity not counted);
- requests without an answer.

Primary analysis and rule
A backend matches Jev on a dataset if, paired on the same rows,
  (A) accuracy     >= Jev's - 2.0 points   (the bar used throughout stages 4 and 5),
  (B) AUC          >= Jev's - 0.02,
  (C) Brier score  <= Jev's + 0.02.
A backend "can replace Jev as the default backend" only if A, B and C all hold on all three datasets. Point estimates decide.
A bootstrap over rows (2,000 resamples; rows are reviews, sentences, pairs) gives a 95% interval for each difference; a result whose
interval contains the bar is reported as decided on the point estimate but not separable from the bar.
A backend that leaves more than 5% of a dataset's requests without an answer fails on that dataset as served; nothing is patched for it.

Calibration reading (the independent check; not a further condition beyond C)
  "as well calibrated as Jev" on a dataset = equal-mass calibration error <= Jev's + 0.02 on the same rows.

Practicality reading (reported next to the rule, not part of it)
- A local backend is practical for batch work on this machine if its rows per second are at least 10% of Jev's on the same dataset.
  Jev's reference figures are its earlier cold runs at concurrency 16: movie 52 rows/s, restaurant single 53 requests/s,
  Walmart-Amazon 38 pairs/s.
- Clef's speed and cost are those of Cloudflare's hosted service. Self-hosting its 27B weights is not tested.
- Requests go through the plain one-state-per-request endpoint, like Jev's. Batch endpoints are not used.

Secondary, reported as such
- Restaurant data with all 21 questions in one request: accuracy, agreement with the backend's own single-question decisions, throughput.
- Recalibration with human labels only: a + b * logit(p) fitted on 200 randomly drawn labelled rows, scored on the remaining rows,
  200 draws, for every source including Jev (restaurant data: one a, b for all 21 predicates, fitted on 200 sentences).
- Rows over a backend's validated window (kev-4b 8,192 tokens, laya 512, clef 65,536), identified from the token counts the backend
  reports; they are not dropped, and a second table is restricted to rows that fit. By character counts no row is expected to exceed any window.
- The same rule A-C applied to the DeepSeek token probabilities on the two datasets where they exist.

Constraint
No Jev output is used to train, fine-tune, calibrate or pick a threshold for any open model. Jev appears only as the comparison column.
Jev's cached judgments stay on this machine and out of the repository.
